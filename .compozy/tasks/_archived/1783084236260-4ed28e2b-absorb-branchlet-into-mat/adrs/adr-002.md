# ADR-002: Lifecycle Manager Approach for Task Closing

## Status

Accepted

## Date

2026-05-19

## Context

When closing a task (`mat --close`), mat needs to decide how aggressively it manages the end-of-lifecycle workflow. The current behavior (via branchlet) deletes the worktree and copies a `git merge` command to the tmux buffer, leaving merge and branch deletion to the user.

The idea phase established that mat should absorb branchlet's core operations and add auto-merge capability. Three approaches were considered:

- **A (Lifecycle Manager)**: Auto-merge branch into base on close; delete branch only on merge success; alert and stop on conflicts
- **B (Safe Minimalist)**: Never auto-merge; copy command to buffer; branch deletion requires explicit flag
- **C (Full Automation)**: Auto-merge, auto-commit uncommitted work, auto-push to remote

## Decision

Adopt Approach A (Lifecycle Manager). On close, mat will:

1. Check for uncommitted changes — if present, alert and stop
2. Merge the feature branch into the base branch automatically
3. Only delete the branch/worktree if the merge succeeds
4. Support `--no-merge` flag for manual merge control
5. Make merge strategy configurable (`merge-commit` default, `fast-forward` alternative) via `merge_strategy` config option

## Alternatives Considered

### Alternative 1: Safe Minimalist (Approach B)

- **Pros**: User always controls merge and deletion; fewer error states; no risk of unintended merges
- **Cons**: Requires manual paste of merge command; more steps for the common case; inconsistent with the Lifecycle Manager value proposition
- **Why rejected**: The user explicitly chose auto-merge with safety guardrails; the common case (clean merge) should be one command

### Alternative 2: Full Automation (Approach C)

- **Pros**: Single command from "done" to "pushed"; maximum convenience
- **Cons**: Auto-commit and auto-push are high-risk actions that can't be easily undone; could push broken code; user trust issue
- **Why rejected**: Too aggressive for V1; auto-commit hides uncommitted work; auto-push could affect remote branches unexpectedly; violates the principle of transparent operations

## Consequences

### Positive

- Close flow becomes a single command for the common case (clean merge)
- User retains control via `--no-merge` and `merge_strategy` config
- Delete only happens on success — no orphaned branches after failed merges
- Merge strategy is configurable per project via `.mat.toml`

### Negative

- Auto-merge introduces new error states: merge conflicts, branch divergence, unrelated histories
- Users must handle merge conflicts manually after mat alerts them
- Close flow is no longer a simple "delete and copy command" — it's a multi-step operation with branching logic

### Risks

- **Merge conflicts on close**: Mat must detect conflicts, print a clear message, and leave both branches intact. Users must resolve conflicts manually.
- **Unintended merges on wrong base branch**: If the base branch detection is wrong (e.g., user was on `develop` but closes into `main`), the merge could go to the wrong place. Mitigated by showing the merge target in the confirmation prompt.
- **Performance on large repos**: Auto-merge adds latency to the close operation. Mitigated by clear status messages during the merge.
