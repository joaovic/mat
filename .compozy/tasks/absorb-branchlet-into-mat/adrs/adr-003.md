# ADR-003: Module Architecture and Error Handling Strategy

## Status

Accepted

## Date

2026-05-19

## Context

The current mat codebase is a single 505-line `main.rs` with 22 functions, no custom error types, `Result<T, String>` everywhere, and 11 `std::process::exit(1)` calls scattered across handler functions. This makes testing impossible and composability difficult. The PRD requires adding config management, no-worktree mode, TMUX auto-detection, auto-merge on close, and CLI subcommands — all of which will significantly increase code volume.

## Decision

1. **Module split**: Split `main.rs` into modules with clear responsibilities:
   - `cli` — CLI argument parsing (clap derive)
   - `config` — TOML config loading, merging, and `mat config` subcommand handlers
   - `display` — Styled output functions (print_error, print_success, print_info, print_tip)
   - `git` — All git command invocations behind a `GitClient` struct
   - `tmux` — All tmux command invocations behind a `TmuxClient` struct
   - `naming` — Name generation (app_name, worktree_name, branch_name, window_name)
   - `commands/create` — Create workflow handler
   - `commands/close` — Close workflow handler
   - `commands/config` — Config subcommand handlers
   - `error` — `MatError` enum and error conversion

2. **Custom error type**: Define `MatError` enum with variants for `Git`, `Tmux`, `Config`, `Validation`, and `Io` errors. Convert all `Result<T, String>` to `Result<T, MatError>`. Remove all `std::process::exit()` calls from handler functions. Single exit point in `main()`.

3. **CommandRunner trait**: Define a `CommandRunner` trait with `RealRunner` (shells out via `std::process::Command`) and `MockRunner` (returns canned output for tests). `GitClient` and `TmuxClient` accept a `CommandRunner` via generic or trait object, enabling unit testing.

## Alternatives Considered

### Alternative 1: anyhow crate

- **Pros**: Less boilerplate; flexible context attachment; widely used in Rust ecosystem
- **Cons**: Loses typed pattern matching; harder to handle specific error cases differently; less idiomatic for a CLI tool with known error categories
- **Why rejected**: Mat has well-defined error categories (git failures, tmux failures, config errors, validation errors) that benefit from typed variants

### Alternative 2: Keep Result<T, String>

- **Pros**: No refactoring needed; consistent with current code
- **Cons**: No type safety; no pattern matching on error categories; impossible to handle git vs tmux errors differently; cannot add context to errors
- **Why rejected**: The refactoring is necessary for testability and maintainability

### Alternative 3: Lib + binary crate split

- **Pros**: Enables integration testing via lib crate; clean separation of logic and entry point
- **Cons**: Adds crate management overhead; premature for current scale; current module split provides similar benefits without the crate boundary
- **Why rejected**: Module split is sufficient for V1; can split into lib+binary later if needed

## Consequences

### Positive

- All business logic becomes unit-testable via MockRunner
- Error handling is consistent and typed
- Single exit point in main() enables proper error reporting and exit codes
- Module boundaries make it clear where to add new features (config, no-worktree, auto-merge)
- Each module can be tested in isolation

### Negative

- Significant refactoring effort for existing code (505 lines across 22 functions)
- MockRunner implementation needs maintenance when new git/tmux commands are added
- More boilerplate for the CommandRunner trait and error type

### Risks

- **Refactoring scope**: Converting 11 exit points to Result propagation touches every handler function. Mitigate by doing this as the first implementation step before adding new features.
- **Trait object vs generic**: Using trait objects (`Box<dyn CommandRunner>`) adds dynamic dispatch overhead; using generics (`<R: CommandRunner>`) adds compile time. For a CLI tool, the overhead is negligible; recommend generics for testability.
