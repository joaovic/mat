# ADR-004: CLI Subcommand Structure and Config Management

## Status

Accepted

## Date

2026-05-19

## Context

The current CLI uses flat positional args (`mat feat login`) and flags (`--close`, `--source`). The PRD adds `mat config list/get/set` subcommands, plus `--no-worktree`, `--no-merge`, and `--use-tmux` flags. The PRD also requires two-tier TOML config (global `~/.config/mat/config.toml` + project-local `.mat.toml`) with `serde` deserialization and manual merging.

## Decision

1. **CLI subcommands**: Restructure the CLI using clap subcommands:
   - `mat <task_type> <task_name>` — create mode (default behavior, same as current)
   - `mat --close` / `mat close` — close mode
   - `mat config list` — list effective config values
   - `mat config get <key>` — show a single config value
   - `mat config set <key> <value>` — set a config value (with `--global` flag)
   
   Flags remain as flags: `--source`, `--no-worktree`, `--use-tmux`, `--no-merge`.

2. **Config management with serde + toml**: Hand-roll config loading using `serde::Deserialize` and the `toml` crate. Implement:
   - `Config` struct with `serde::Deserialize` for all config keys
   - `Default` impl providing hardcoded defaults
   - `load()` function that: loads global → loads local → merges local overrides global
   - `set()` function that writes to the appropriate TOML file
   - Merge strategy: project-local overrides global; CLI flags override both

3. **Worktree path**: Default to `{repo_dir}.worktree/{worktree_name}/`, configurable via `worktree_root` config key. Supports branchlet-style template-like naming with `{app}`, `{type}`, `{name}` placeholders.

## Alternatives Considered

### Alternative 1: Flat flags for config

- **Pros**: No subcommand structure change; `mat --config-list`, `mat --config-get key`
- **Cons**: Not idiomatic for CLI tools; doesn't scale to multiple config operations; conflicts with existing flag namespace
- **Why rejected**: Subcommands are the standard pattern for multi-operation CLIs; `mat config` is cleaner and extensible

### Alternative 2: `config` crate for layered config

- **Pros**: Production-grade merging, type coercion, multiple format support, environment variable overrides
- **Cons**: Adds ~15 transitive dependencies; over-engineered for 5 config keys; TOML-only is simpler
- **Why rejected**: Manual serde + toml is sufficient for 5 config keys and two-tier merging; avoids unnecessary dependency bloat

### Alternative 3: `confy` crate for zero-config

- **Pros**: Single function to load/save config; minimal boilerplate
- **Cons**: Limited to single-file config; no two-tier support; no `mat config set` command support
- **Why rejected**: Cannot support two-tier (global + project-local) config; cannot handle set operations

## Consequences

### Positive

- CLI structure is extensible: new subcommands (list, switch, status) fit naturally
- Config management is transparent and debuggable (`mat config list` shows sources)
- serde + toml keeps the dependency tree minimal (toml crate is already a transitive dep via clap)
- Worktree path is configurable per project

### Negative

- Existing users must adapt to `mat close` instead of `mat --close` (or support both)
- Config merge logic must be hand-tested (no library handles "show where each value comes from")
- TOML file writing must preserve comments and formatting (or accept that `mat config set` may reformat)

### Risks

- **Backward compatibility**: `mat --close` is the current usage pattern. The subcommand form `mat close` changes this. Mitigate by supporting both `--close` flag and `close` subcommand, with a deprecation notice on `--close`.
- **TOML writing**: The `toml` crate's `to_string()` may reformat files when writing. Mitigate by only writing changed keys, not rewriting the entire file, or using `toml_edit` crate for comment-preserving edits.
